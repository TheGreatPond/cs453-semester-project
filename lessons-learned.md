I feel that the most important technical concept that I learned with this project was how web tokens are used to authenticate users over APIs. Within my line of work in IT I have interacted with other command line tools such as RedHat OpenShift's OC cli tool which also allows authentication based on a token provided after providing credentials, but this project gave more context on how tokens are used to authenticate with an API
For similar projects in the future i would recommend ensuring that database design, authentication, and authorization are all considered together from the beginning to save time correctly implementing role based accessed to restricted resources during the initial stand up of the project rather than the problem I had of first implementing the entire database of users, projects, and task and then having to rewrite many of the routes to check for user roles or ownership of the requested resources to then grant access to them. This problem of having to rewrite much of my code did not stop with just adding authorization on to protected routes.

Due to a failure on my part to initially organize my code into separate files, I had to relocate many of my routes to their corresponding files, which later caused me to then have to fix imports that were no longer accurate. I also failed to use an env file into much later in my code which caused me to have to rework some smaller details very late into my projects development cycle

Many of these issues traceback to not taking the time at the beginning of this project to read through all of the relevant documentation to see what would need to be done in the longer term. If I were to start this project again, the best advice that I could give would be to spend more time planning all routes mentioned in all documentation rather than working through one at a time. I would also develop test using “vitest” much earlier into the development of my project since my approach for this project was instead to develop an OpenAPI doc that, while useful for testing individual routes and slight variations on them, was ultimately a much slower testing suite compared to just running “npm test” to ensure i hadn’t broken any previously running functionality.

One design decision that I made before reading how we were intended to use roles for permissions was to create the project_members table. I intended this table to be the source of truth for all permissions within my project before reading that I was required to have a role field on my users and while it does add complexity in that it is another table to track. I believe that this additional table could have been used to give more granular permissions. For example a user could have been given admin rights within a project to add or remove other users from the project, while not being given admin over every project which is how the application is currently setup.

With this in mind,I would highly encourage the next team to dive deeper into the more granular permissions mentioned above as well as building an auditing system so that if a user did get permissions to a resource that they should not have had access to, there could be access logs to find what data had been exposed.
